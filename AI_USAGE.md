# AI Usage

Ведётся по ходу разработки, а не восстанавливается по памяти в конце. Разделы дополняются по мере того, как проект продвигается — сейчас закрыты инфраструктура, API-слой, MSW, список аукционов.

## SDD-пайплайн

Разработка идёт по спекам — спека пишется и проверяется до того, как пишется код фичи. Процесс закреплён проектными Claude Code skills (`.claude/skills/`):

1. **[intake-requirements](.claude/skills/intake-requirements/SKILL.md)** — приём исходного ФТТ/ТЗ. Требует на входе бэкенд-контракт (OpenAPI/Swagger/JSON-схема) и ссылку на Figma. Уточняет неоднозначные бизнес-требования, предлагает варианты имплементации с явным трейд-оффом, разбивает подтверждённый объём на список фич.
2. **[write-spec](.claude/skills/write-spec/SKILL.md)** — по одной фиче пишет `specs/<slug>.md` (Goal/Scope/Acceptance Criteria/Edge Cases), каждый критерий приёмки трассируется к реальному полю/enum схемы, а не к формулировкам вроде «удобно» или «работает хорошо».
3. **[review-specs](.claude/skills/review-specs/SKILL.md)** — сверяет уже написанные спеки между собой (общие сущности/enum названы одинаково, нет противоречий, нет потерянных или задвоенных критериев) до того, как что-либо идёт в реализацию.
4. **[implement-spec](.claude/skills/implement-spec/SKILL.md)** — реализация одной фичи в новой сессии: подтягивает только нужные фрагменты схемы, ближайший готовый слайс как образец конвенций, заводит задачи (или, если фича уже реализована — чек-лист по Acceptance Criteria вместо задач). Никогда не создаёт/не переключает git-ветки сам — ожидает, что нужная ветка уже выбрана.

Каждая фича — своя ветка, реализуется последовательно (не параллельно — конфликтов в общем воркинг-дереве это исключает без git worktree), PR в `main` гоняет [CI](.github/workflows/ci.yml) (lint → typecheck → test → build).

Пример прогона всего пайплайна на уже готовой фиче (демонстрация механики `implement-spec`) и найденный по итогу реальный баг (утечка адреса в моке `/auctions/list` мимо флага `hide_points_address_and_contacts`) — см. `src/shared/mocks/db/store.ts` и его тест.

## Решения и правки от пользователя в диалоге

Момент, где направление менялось не по инициативе ИИ, а по прямому решению/правке в диалоге.

- Настояла на разнообразных filler-данных в сиде (город/тип/статус/цена/дата на каждую запись), а не минимально достаточных для появления пагинации — чтобы фильтры реально было чем проверить, а не просто «не падают».
- Спроектировала многоагентный SDD-флоу (`intake-requirements` → `write-spec` → `review-specs` → `implement-spec`).

## Что бы улучшили при наличии ещё одного дня

- **Сортировка списка аукционов.** Сейчас не реализована — не входила в явные требования задания к списку (только пагинация, фильтры, состояния, prefetch), но схема её поддерживает (`AuctionListRequest.sort: {start_time, price_per_km, current_price}`), а собственный же MSW-хендлер её игнорирует, обрабатывая только `is_oldest`. Стоило бы:
  (а) - довести хендлер до полноценной поддержки `sort`,
  (б) - добавить сортировку в UI.
- **Полный набор фильтров из схемы.** Сейчас реализован обязательный минимум из задания (cargo_num, status, statuses, auc_type, load_city/unload_city, диапазон дат погрузки, is_available, is_bidder, цена от/до) — этого достаточно по ТЗ, но `AuctionListRequest` поддерживает заметно больше: диапазоны веса/объёма, body_types, is_international_shipment, customer/customer_ids, contractor, auction_ids, диапазоны create_date/start_time/stop_time, load_range/unload_range с gc_id. MSW-хендлер уже частично готов к части этого (`is_favorite`, `price_per_km_from/to` он умеет, просто в UI не выведены), но большинство перечисленного не поддерживает даже мок — потребовалось бы сначала расширить хендлер, потом UI.
- **UI/UX-полировка.** Список того, что сейчас нарочно упрощено ради срока: выбор города — обычный `<select>`, а не поисковый комбобокс (неудобно при росте словаря городов за пределы 12 моковых); диапазон цены — два числовых инпута, а не слайдер с разметкой; мобильная панель фильтров разворачивается инлайн, а не как полноценный bottom sheet с оверлеем/свайпом-закрытием; нет debounce на текстовых фильтрах (номер заявки, город) — каждое применение фильтра требует явного клика «Применить», что верно, но не даёт живого поиска по вводу.
